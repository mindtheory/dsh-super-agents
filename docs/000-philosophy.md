# 000 理念（Philosophy）

> 本文档系列以 dsh-super-agents 为参照实现，但面向任何想构建"自主智能体系统"的项目共享。
> 思想基准：DeepSeek 官方研究原型 [dsh-superagent-prototype](https://github.com/deepseek-ai/dsh-superagent-prototype)
> （"Towards a More Autonomous Agent System"），并结合我们在 DSH 宿主上的落地经验做了裁剪与扩展。
> 各编号文档只依赖前面的文档，请按序阅读。

## 核心原则

**拿走尽可能少的人类注意力，给出尽可能多的价值。**
（Take as little human attention as possible, and give as much value as possible.）

系统的每一部分都用它消耗的注意力来衡量：一条消息、一次通知、一个提问、一个设置项、
一个面板元素、一段文档，都在花别人的注意力——它必须给出超过这个成本的价值，否则就删掉。

一个能替整个团队干活的 agent，同样能浪费整个团队的注意力。所以：

- **只在被要求、或团队写下的规则允许时行动。** 请求必须直接指向 agent、且来自被允许的人。
  没人要求的主动工作必须有成文规则，且默认先只记录"本来会做什么"（observe 模式），不真动手。
- **只在人必须行动、或能用上结果时说话。** 确认一次请求并说明要做什么；干活期间保持安静；
  结果就绪、需要决策、或干不完时再说话。消息要短，回到提出请求的对话去说。
- **一次只问一个具体问题**，用结构化形式，让问题真正到达人，而不是埋进长篇报告。
- **按影响停下，而不是按工作量。** 本地改动一路做到可评审的结果；需要设计决定的改动
  带着一个清晰的问题停下。
- **诚实地报告。** 草稿标记为未完成，失败报告为失败，遇到限制绝不绕过——绕过限制本身就是错误。

## 对设计的要求

- **概念要少。** 设计只有它的领域概念（Agent、Schedule、Run、Playbook）和它们的具体实现。
  一个业务需求要么成为某个概念的属性，要么成为 agent 遵循的一段提示词，不轻易新增概念。
- **设置要少。** 一个值适合几乎所有场景时，用默认值取代设置项。团队用文字描述的行为
  是提示词文本，不是设置。
- **面板只显示需要人的事。** 待办优先；健康状态不占空间；一个数字只有在它会改变监督者的
  动作时才出现。
- **文档按序构建。** 每篇编号文档只建立在前面的文档之上，读者永远不需要一个尚未引入的概念。

## 责任（对操作者）

agent 用你团队天天见到的账号发言、提交、干活。它发出的每条消息都在花同事的注意力，
你要为此负责：

- **从窄开始。** 允许名单先短，主动工作先只记录。确认"本来会做的"都对之后再放宽。
- **调噪不降噪加。** agent 吵了，就把提示词改短改严，或者暂停它；不要为解释噪音再加消息。
- **不要用它刷量。** 批量 PR、广播消息、瞎忙，花掉团队的比给出的多。
- **为它说的话负责。** 读它以你名义发的内容，错了就在提示词里纠正。

目标是：对的时间给对的帮助，其余时间什么都没有。

## 本项目的立场

dsh-super-agents 把"超级智能体"做成 DSH 宿主里的一个插件：**持久化的 agent 角色卡（配置即数据）、
可自主领活的调度器、后台执行会话、每次运行后自动蒸馏经验（playbook）的自学习回路**。

与官方原型的关系：原型是"面向一个 GitHub 仓库的团队级主动 agent"（GitHub/飞书事件 → 授权评估 →
工单 → 执行会话），我们是"个人/小团队在 DSH 内的常驻 AI 员工"。领域不同，但理念同源——
本文档系列提炼的是两者共享的、可移植到其他项目的思想与工程原则；两者不一致的地方，
在 [003 工程与解决思路](003-engineering.md) 的"采纳与裁剪"一节里逐条说明理由。
